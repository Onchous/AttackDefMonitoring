# AttackDefMonitoring

Мониторинг и анализ TCP/UDP-трафика для Attack & Defense CTF на базе
[Pkappa2](https://github.com/spq/pkappa2). Эта версия включает добавление сервиса
и запуск захвата через веб-интерфейс, просмотр цепочек запросов и экспорт в Python.

## Возможности

- Добавление сервисов по имени, интерфейсу и портам из **Manage Tags**.
- Автоматический запуск tcpdump и загрузка трафика после сохранения сервиса.
- Сохранение настроек и восстановление захвата после перезапуска контейнеров.
- Повторная отправка pcap при временной недоступности мониторинга.
- Поиск по TCP/UDP, адресам, портам, содержимому и меткам.
- Объединение соединений клиента в цепочки, подсветка флагов.
- Экспорт HTTP-цепочки в Python `requests` с cookies и cookie-based CSRF.
- Выбор событий, отдельный **Full chain .py** и экспорт прямо в DestructiveFarm.
- Подготовка обезличенного запроса для внешнего чата и проверка полученного Python-кода.
- Конвертеры HTTP, DNS, TLS, WebSocket и других протоколов из Pkappa2.

## Развёртывание на другом хосте

Нужны **Linux**, Git и **Docker Engine с Docker Compose v2**. Сборщик использует
сетевые интерфейсы Linux-хоста. Для захвата через UI запускайте проект на хосте,
через который проходит трафик отслеживаемых сервисов.

```sh
git clone https://github.com/Onchous/AttackDefMonitoring.git
cd AttackDefMonitoring
sudo bash scripts/setup.sh
```

Если Docker доступен вашему пользователю, можно запускать без `sudo`.
Первый запуск создаёт `.env` с двумя случайными паролями, собирает сервер и
запускает **оба** контейнера: `pkappa2` и `capture`. Готовые файлы интерфейса
лежат в `web/dist`, поэтому установка npm-пакетов внутри Docker не нужна.
Повторный запуск использует существующий `.env`. Пароли и настройки чужого хоста
не нужны.

Если рядом существует `../DestructiveFarm/client`, setup автоматически подключает
его для кнопки **В DestructiveFarm**. Иначе файлы сохраняются в локальном
`farm_exports`. Путь можно изменить через `DESTRUCTIVE_FARM_CLIENT_DIR` в `.env`.

Откройте `http://IP_ХОСТА:8080`. Логин: `admin`. Пароль веб-интерфейса находится
в `PKAPPA2_USER_PASSWORD` в локальном `.env`; `PKAPPA2_PCAP_PASSWORD` используется
сборщиком для загрузки трафика. По умолчанию доступ использует HTTP; для доступа
через интернет настройте HTTPS-прокси или VPN.

Можно подготовить настройки вручную:

```sh
cp .env.example .env
# Задайте разные пароли PKAPPA2_USER_PASSWORD и PKAPPA2_PCAP_PASSWORD.
# При необходимости измените PKAPPA2_HTTP_PORT и PKAPPA2_BIND_ADDRESS.
mkdir -p farm_exports && chmod g+rws farm_exports
sed -i "s/^PKAPPA2_FARM_EXPORT_GID=.*/PKAPPA2_FARM_EXPORT_GID=$(stat -c '%g' farm_exports)/" .env
sudo docker compose up -d --build
```

После изменений интерфейса обновите хранимую сборку командой
`cd web && npm run build`, затем добавьте изменения `web/dist` в коммит.

В `.env` можно изменить порт веб-интерфейса, например `PKAPPA2_HTTP_PORT=8090`.
Адрес загрузки сборщика автоматически использует тот же порт. Для HTTPS-прокси
на этом же хосте можно задать `PKAPPA2_BIND_ADDRESS=127.0.0.1`.

## Добавление сервиса и автоматический захват

1. Откройте **Manage Tags → Добавить сервис и захват**.
2. Введите имя сервиса, выберите интерфейс и укажите порты: `7070` или `7070,8080-8081`.
3. Нажмите **Сохранить и запустить захват**.
4. Отправьте запрос к отслеживаемому сервису. Трафик появится в поиске после загрузки и индексации.

`lo` подходит для обращений через localhost. Для входящих сетевых запросов
выберите реальный интерфейс вашего хоста: `eth0`, `ens18`, `tun0` и т. п.
Список берётся с текущего хоста. `any` собирает трафик со всех интерфейсов.

После сохранения создаётся метка сервиса, сборщик запускает захват TCP и UDP
и публикует полные записи pcap примерно каждые 2 секунды. Docker и systemd
вручную для каждого сервиса настраивать не нужно. В **Manage Tags** видны
состояние захвата и ошибки; там же можно изменить порты или остановить сбор.

Сборщик наблюдает существующие сервисы. Их приложения нужно запустить отдельно.
Не добавляйте порт самого мониторинга в захват: загрузка pcap создаёт дополнительный трафик.

## Цепочки и экспорт

Нажмите строку результата поиска, чтобы открыть цепочку соединений клиента.
Кнопка **Разобрать** находится сразу под верхней панелью открытого соединения.
Цепочка объединяет события одного IP клиента с паузой не больше секунды, включая
переходы между портами сервисов. События показаны компактными строками; сырой
запрос и ответ раскрываются по нажатию. Можно выбрать нужные
события, быстро оставить шаги до ответа с флагом или убрать статические файлы.

**Python** показывает код выбранных шагов, **Full chain .py** скачивает всю
цепочку, а **В DestructiveFarm** сохраняет проверенный исполняемый файл в каталог
клиента фермы. Неподдерживаемый TLS/UDP-поток отмечается и пропускается, не ломая
остальные HTTP-шаги.

```sh
python3 -m pip install requests
python3 replay-chain.py IP_СЕРВИСА
```

Экспорт поддерживает HTTP/1.x и печатает ответы через `print(r.text, flush=True)`.
HTTPS, HTTP/2 и WebSocket можно просматривать через конвертеры; экспорт в
`requests` для этих протоколов недоступен. Подробности и ограничения описаны
в [руководстве по захвату и цепочкам](docs/capture-and-chains.md).

Кнопка **Разобрать** формирует запрос только из выбранных событий и скрывает
флаги и секретные значения. Скопируйте запрос в выбранный чат, затем вставьте
полученный ответ обратно: мониторинг извлечёт Python и проверит
`IP = sys.argv[1]`, одну `requests.Session()`, вывод после каждого запроса,
адреса назначения и опасные вызовы. Код не запускается во время проверки.

## Управление

```sh
sudo docker compose ps
sudo docker compose logs --tail=100 capture pkappa2
sudo docker compose restart
sudo docker compose down
```

Индексы и импортированный трафик хранятся в томе `pkappa2-data`, настройки
захвата и очередь загрузки — в `capture-state`. Обычный `docker compose down`
сохраняет эти данные; `down -v` удаляет тома вместе с данными.

Обновление:

```sh
git pull --ff-only
sudo docker compose up -d --build
```

Если UI сообщает `Capture collector unavailable`, проверьте, что запущены
оба контейнера, и посмотрите `docker compose logs capture`. Для ошибки загрузки
проверьте совпадение `PKAPPA2_PCAP_PASSWORD`, свободный веб-порт и доступность
`http://127.0.0.1:ПОРТ` на хосте. После смены `.env` примените `docker compose up -d`.

## Трафик с отдельного вулнбокса

Для удалённого источника используйте загрузку pcap или PCAP-over-IP из
[руководства Pkappa2](docs/pkappa2-guide.md). Интерфейсы в UI относятся к хосту,
где работает контейнер `capture`.

Для Linux-хостов с systemd также сохранён дополнительный CLI-сборщик:

```sh
sudo scripts/capturectl.sh add eth0 7070 5001
sudo scripts/capturectl.sh status eth0 7070
sudo scripts/capturectl.sh remove eth0 7070
```

CLI требует `tcpdump`, `curl`, `flock`, `ip` и systemd. Он устанавливает копию
сборщика в `/opt/pkappa2-capture`, а конфигурацию — в `/etc/pkappa2-capture`.
По умолчанию отправляет pcap на `http://127.0.0.1:8080`; другой адрес задаётся
через `UPLOAD_URL` в настройках соответствующей systemd-службы.
При переносе порта из CLI в UI сначала остановите его старую службу.

## Разработка и проверки

Для ручной сборки нужны Go 1.25+, `libpcap-dev`, Node.js 24 и Yarn 1.x.

```sh
cd web
yarn install --frozen-lockfile
yarn build
python3 -m pip install requests
npm run test:chains
cd ..
python3 -m unittest discover -s capture/tests -v
go test ./...
go run ./cmd/pkappa2
```

GitHub Actions проверяет сборку интерфейса, экспорт цепочек, Go и Python,
а также собирает и запускает Docker Compose на чистом Linux-хосте с проверкой
добавления сервиса, захвата, загрузки и поиска тестового HTTP-трафика.
