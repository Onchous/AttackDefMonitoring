# Захват через UI и экспорт цепочек

## Первый запуск на своём Linux-хосте

```sh
git clone https://github.com/Onchous/AttackDefMonitoring.git
cd AttackDefMonitoring
sudo bash scripts/setup.sh
```

Команда запускает Pkappa2 и сборщик `capture`. Обновите вкладку
`http://IP_ХОСТА:8080`. Логин `admin`, пароль из `PKAPPA2_USER_PASSWORD` в `.env`.
Для уже развёрнутой версии выполните `sudo docker compose up -d --build`
и обновите страницу через Ctrl+Shift+R.
Важно запустить оба сервиса: команда с одним аргументом `pkappa2` не запускает
сборщик. Для диагностики: `sudo docker compose logs --tail=50 capture`.

## Добавить локальный сервис

1. Откройте **Manage Tags → Добавить сервис и захват** (или CTF Setup Wizards → Setup Service ports).
2. Укажите название, порт (например `7070`) и интерфейс.
3. Нажмите **Сохранить и запустить захват**.

`lo` — соединения через localhost, `eth0` — входящий трафик через сетевой
интерфейс вулнбокса. Список интерфейсов берётся с вулнбокса.
Можно задать несколько портов: `7070,8080-8081`.

Для уже созданной метки сервиса нажмите значок сети в её строке Manage Tags:
порты будут подставлены, останется выбрать интерфейс и запустить захват.
Добавление сервиса из поиска по `sport:7070` также открывает эту форму.

После сохранения сборщик начинает захват TCP и UDP. Завершённые пакеты
публикуются каждые 2 секунды без перезапуска tcpdump и отправляются в Pkappa2.
Трафик появляется после реальных запросов к сервису; сам сервис мониторинг
не запускает. На первой странице поиска результаты обновляются автоматически.
При открытой цепочке просмотр остаётся стабильным.

В Manage Tags видны интерфейс, порты, состояние и ошибки загрузки. Там же можно
изменить настройки или остановить захват. При ошибке запуска UI не показывает
успешный запуск. Настройки переживают перезапуск контейнеров; pcap при ошибке
загрузки остаются в очереди и отправляются повторно.

Сборщик работает в сетевом пространстве хоста, чтобы видеть `lo` и сетевые
интерфейсы вулнбокса. Его API доступен через общий Unix-сокет и API авторизации
Pkappa2; отдельного публичного порта управления нет. Docker socket не монтируется,
контейнер не использует privileged. Один процесс на интерфейс обслуживает
объединённые порты всех его сервисов, предотвращая двойной захват одинакового
порта в нескольких сервисах.

Прежние службы из `scripts/capturectl.sh` независимы от нового UI.
Если переносите уже захватываемый порт в UI, сначала остановите его старую службу:

```sh
sudo scripts/capturectl.sh remove lo 7070
# Для прежней службы из первоначальной настройки:
sudo systemctl disable --now pkappa2-capture5001
```

Останавливайте только службу переносимого порта; остальные могут продолжать
работать. CLI остаётся доступен для прежней настройки.

## Компактные цепочки

Список сохраняет табличный вид: Tags, Client, Bytes, Server, Duration, Time.
Рядом с клиентом показано число сессий. Соединения одного IP объединяются,
пока следующее начинается не позже чем через секунду после окончания предыдущего.
Длинное keep-alive соединение остаётся целиком в одной цепочке.

Подсчёт загружает также соединения этого клиента вне текущего фильтра и страницы.
Поэтому фильтр по флагу не отрезает регистрацию или вход из этой цепочки.
Во время уточнения числа сессий рядом с ним виден индикатор загрузки.

Нажмите строку: нижняя панель покажет запросы и ответы всех соединений цепочки.
Кнопка **Скопировать kill chain** копирует всю последовательность, **.py**
скачивает скрипт, **Python** показывает его код. Эти кнопки доступны и в
обычном просмотре одного соединения — экспорт всё равно включает всю его цепочку.

Флаг `[A-Z0-9]{31}=` всегда подсвечивается ярко-жёлтым с чёрным текстом
в запросах и ответах, включая флаги на границе блоков данных.
Регулярки из `tag/flag_in` и `tag/flag_out` также учитываются.

## Формат фермы

Экспорт представляет собой читаемый Python-код:

```python
#!/usr/bin/env python3
import requests
import sys

IP = sys.argv[1]
s = requests.Session()
r = s.get(f"http://{IP}:7070/profile", headers={"Host": "localhost:7070"},
          allow_redirects=False, timeout=30)
print(r.text, flush=True)
```

Все запросы идут по порядку через одну сессию. Порт, путь, query-параметры,
тела (в том числе бинарные) и заголовки сохраняются из трафика.
IP сервера заменяется аргументом фермы. Каждый ответ, включая ответ с флагом,
печатается через **`print(r.text, flush=True)`**. Скрипт не выводит служебные
строки в stdout и не выполняется автоматически мониторингом.

Cookies обновляются из ответов; значения захваченных cookies используются
только при отсутствии новых. Cookie-based CSRF в URL, теле или заголовках
заменяется на новое значение cookie. `Host` сохраняется для виртуальных хостов.
`Content-Length`, `Transfer-Encoding` и `Accept-Encoding` рассчитывает requests,
чтобы изменённая длина токена или неподдерживаемое браузерное сжатие не ломали запрос.
Перенаправления выполняются как отдельные захваченные запросы.

Запуск вне фермы:

```sh
python3 -m pip install requests
python3 replay-chain.py 172.18.0.3
```

Поддерживается обычный HTTP/1.x: фрагментированные запросы, несколько запросов
в соединении и chunked-тела. HTTPS, HTTP/2, WebSocket, произвольный TCP/UDP
и неполные запросы дают явную ошибку экспорта, но их трафик можно просматривать.
Токены из JSON/HTML и серверные ID, которые не хранятся в cookies, могут
потребовать ручной правки скрипта. Регистрация с уже занятым логином также
зависит от поведения сервиса.

## Проверки разработки

```sh
cd web
npm run build
npm run test:chains   # Python-интеграция требует установленный requests
cd ..
python3 -m unittest discover -s capture/tests -v
go test ./...        # Требуются Go и libpcap-dev
```
